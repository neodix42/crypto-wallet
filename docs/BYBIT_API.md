# Bybit V5 transport contract

The Exchange extension is explicitly requested by the owner. It introduces a custodial exchange account alongside the existing local wallet. API access does not make exchange-held funds noncustodial. The HTTP client is `internal/exchange/bybit`; Go core performs requests and the isolated Go signer owns credentials and authorization. No third-party exchange SDK was added.

API research was checked against the official documentation on 2026-10-24. Private exchange calls and funded transactions were **NOT_RUN**: development uses public synthetic credentials and isolated HTTP/TLS fixtures. Package tests establish wire/schema and failure behavior; they do not establish Bybit acceptance, account eligibility, liquidity or successful mainnet deposits/withdrawals.

## Transport and authentication

`New(endpoint, Authorizer)` accepts only exact production HTTPS authorities listed by the [official integration guide](https://bybit-exchange.github.io/docs/v5/guide). The returned `Endpoints()` list is copied. Regional domains are selected explicitly, including the UAE domain; a geographic location is not inferred from the machine. Testnet/custom/loopback URLs, alternate ports, user info, paths, fragments and redirect targets are rejected. The production transport has no environment proxy, cookie jar or redirect following. TLS validation is enabled, TLS 1.2 is the minimum, request timeouts and connection limits are finite, and response headers/bodies are bounded. Public market requests carry no private authorization.

For a private request the authorizer receives the exact endpoint, method, fixed path, canonical query/body, current timestamp and 5-second window. GET keys are sorted and URL encoded, including opaque cursor values. POST JSON is marshaled from one of three fixed DTOs; unknown/duplicate fields, extra authority, margin, derivatives and noncanonical encoding fail closed. The pure `ValidateAuthRequest` check grants no approval. The signer must separately match state-changing requests to a durable, immutable, password-authorized operation. User interaction must finish before the final request timestamp is captured.

The [documented HMAC input](https://bybit-exchange.github.io/docs/v5/guide) is timestamp, API key, receive window and exact query/body. **Bybit does not cryptographically include HTTP method, path or endpoint.** The local policy checks those fields and the network client uses the approved descriptor, but a compromised Go network core could replay an unexpired signature to another API endpoint accepting the same payload. Go core is therefore trusted with exchange authorization transport. No claim of cryptographic path binding against a compromised core is made. Credentials should have the minimum permissions and an appropriate IP restriction; secrets stay in the encrypted vault/isolated prompt boundary.

HTTP errors expose numeric status only; exchange errors expose numeric `retCode` only. Raw response messages, transport errors, bodies, headers and credentials are never copied into error text. JSON rejects duplicate fields, invalid UTF-8, excessive nesting and trailing data. Responses remain typed with exact decimal strings. State-changing requests have no automatic retry. An HTTP acknowledgment is not execution or on-chain finality.

## Fixed API surface

| Function | Official endpoint and enforced purpose |
| --- | --- |
| `APIKeyInfo` | [API key information](https://bybit-exchange.github.io/docs/v5/user/apikey-info): numeric UID, read-only/master flags and Spot/Wallet permissions, without forwarding the echoed API key or secret field |
| `CoinInfo` | [Coin information](https://bybit-exchange.github.io/docs/v5/asset/coin-info): full chain IDs/types, full token contracts, deposit/withdrawal suspension, precision, minima and fees |
| `DepositAddress` | [Master deposit address](https://bybit-exchange.github.io/docs/v5/asset/deposit/master-deposit-addr): exact selected coin and chain, address and tag/memo; rejects a different/ambiguous returned chain |
| `AccountBalance` | [Single-coin balance](https://bybit-exchange.github.io/docs/v5/asset/balance/account-coin-balance): FUND or UNIFIED, distinct wallet/transfer/safe amounts; requests transfer safety for the opposite account type |
| `SpotInstrument` | [Instrument information](https://bybit-exchange.github.io/docs/v5/market/instrument): a Trading spot pair with USDT quote, exact precision, current market maximum and minimum order value |
| `SpotTicker` | [Ticker](https://bybit-exchange.github.io/docs/v5/market/tickers): last/best bid/best ask prices for the exact spot symbol; the last price is an observation, never a guaranteed execution price |
| `SpotFeeRate` | [Trading fee rate](https://bybit-exchange.github.io/docs/v5/account/fee-rate): exact symbol's maker/taker rate |
| `CreateOrder` | [Place order](https://bybit-exchange.github.io/docs/v5/order/create-order): `spot`, `Market`, `isLeverage=0`, unique `orderLinkId`; Buy spends `quoteCoin`, Sell spends `baseCoin`; explicit Percent slippage 0.01–10 with at most two decimals |
| `FindOrder` | [Realtime order](https://bybit-exchange.github.io/docs/v5/order/open-order), then [history](https://bybit-exchange.github.io/docs/v5/order/order-list): exact symbol/link identity; recent closed orders can disappear from realtime after server restart |
| `Executions` | [Execution list](https://bybit-exchange.github.io/docs/v5/order/execution): up to 100 fills per explicit page, exact order/symbol identity, unique execution IDs and preserved fees/currencies |
| `Transfer`, `TransferStatus` | [Internal transfer](https://bybit-exchange.github.io/docs/v5/asset/transfer/create-inter-transfer) and [records](https://bybit-exchange.github.io/docs/v5/asset/transfer/inter-transfer-list): UUID identity, only FUND ↔ UNIFIED under the same UID, exact amount and explicit pending/unknown states |
| `Withdraw`, `WithdrawalRecords` | [Withdraw](https://bybit-exchange.github.io/docs/v5/asset/withdraw) and [records](https://bybit-exchange.github.io/docs/v5/asset/withdraw/withdraw-record): FUND, forced on-chain, exact selected chain/address/tag, `feeType=1` and alphanumeric 1–32 character request ID |
| `DepositRecords` | [On-chain deposit records](https://bybit-exchange.github.io/docs/v5/asset/deposit/deposit-record): coin/transaction identity, up to 50 records per explicit page; preserves chain/address/tag, deposit status, fee, deposit restrictions and Travel Rule state |

FUND/UNIFIED transfers and spot execution are distinct operations. Transferable balance is not labeled as free spot balance; debt, locks and margin collateral may restrict a UNIFIED account. There is no borrowing, leverage, derivatives, arbitrary order, API-key management or generic authenticated HTTP API.

Execution fees include the documented `extraFees` records, including UAE VAT and Indian GST. The [private execution schema](https://bybit-exchange.github.io/docs/v5/websocket/private/execution) defines the inner fee coin/type/subtype/rate/amount, and the [REST execution endpoint](https://bybit-exchange.github.io/docs/v5/order/execution) returns the additional information as JSON text. The bounded parser accepts those documented representations with exact decimal strings and known tax pairs. It rejects missing/null metadata, malformed/unknown records and extra authority. For the supported market-taker flow all ordinary fees and taxes must use the received asset, and their sum cannot exceed the gross receipt. An input-asset fee, unexpected fee coin or incomplete metadata keeps reconciliation UNKNOWN; it cannot authorize additional spending or disappear from a reported fee total. This remains an exchange-reported result.

## Asset identity and remaining constraints

The API layer takes an already verified chain selection. It never infers a chain from a ticker, EVM address or guessed string such as `APTOS`. Wallet integration must match the wallet's actual mainnet network and native/token identity against full coin metadata, then use that metadata's exact chain ID. The deposit-address API exposes only a suffix of the token contract; that suffix is insufficient to establish token identity. Its full contract must come from coin information and match the wallet registry. Suspended/unsupported or ambiguous mappings remain unavailable; existing wallet networks are not removed.

TON deposits may need a tag/memo even though withdrawing to this application's own TON wallet does not need an exchange-account memo. The [official deposit instructions](https://www.bybit.com/en-GB/help-center/article/How-to-Make-an-On-Chain-Crypto-Deposit-To-Bybit) warn that omitting the required memo can lose funds. It must be included in the actual signed on-chain payment. A deposit record alone does not bypass Travel Rule, AML, daily caps or withdrawal restrictions.

Bybit requires the master UID for withdrawals and the exact address in its withdrawal whitelist. With `feeType=1`, the entered debit includes Bybit's fee: the recipient receives less. Regional Travel Rule data, account eligibility and additional provider restrictions may be required. UAE withdrawals support the eight legacy beneficiary fields explicitly documented by the [withdrawal endpoint](https://bybit-exchange.github.io/docs/v5/asset/withdraw): country, state, city, building, street, postal code, date of birth and place of birth. They are collected through the masked signer dialog, stored only in the encrypted request journal, and transmitted only to `api.bybit.ae`. The fixed DTO rejects unknown, duplicate, null and malformed fields, future/invalid dates and invalid country codes. Its public operation projection omits these fields. The linked generic questionnaire schema does not document UAE; this integration does not invent one. Other regional questionnaire/beneficiary requirements are not implemented and cannot be bypassed by accepting a provider rejection.

For percentage withdrawal fees, the documented `feeType=1` estimate is fixed fee plus `(input − fixed fee) × percentage`. The coordinator calculates this with integers and rounds the estimate upward at the network's withdrawal precision, leaving the user's amount exact. Withdrawal records label an `amount` and a fee but do not define whether that recorded amount is gross or net. Reconciliation therefore uses the known acknowledgment ID and exact coin/chain/destination/tag, exposes the provider's reported amount and fee separately, and labels a completed status as the exchange's report. It does not infer recipient credit or independent on-chain finality from a guessed amount equation.

Withdrawal `requestId` is an alphanumeric idempotency key, **not** a hyphenated UUID. The documented record query filters by the returned withdrawal ID and does not expose a request-ID lookup. If create is accepted but its acknowledgment is lost, an amount/address/time heuristic cannot prove which withdrawal was made. Keep the operation UNKNOWN and never create an automatic replacement. An absent order/transfer/deposit/withdrawal record also never proves nonacceptance. The caller must retain operation identities, page within documented limits and keep incomplete reconciliation explicit.

Independent exchange acceptance with disposable, capped funds, account-specific restrictions and an independent security review remain **NOT_RUN**. No real credential or public-network trade was used while implementing this client.
