# Historical threat model and remaining trust

> Owner update (2026-10-29): the shipped Wails UI now uses one trusted main window with reusable in-page dialogs and ordinary Wails bindings. It no longer launches a private UI self-role, isolated prompt page or one-use UI pipe. Normal selection/copy/cut/paste are enabled. The main UI is trusted with entered/displayed secrets and approval intent. This supersedes the separate-renderer and noncopyable-secret requirements below, which describe earlier designs. Go signer/core isolation, cryptography, reauthentication and transaction validation remain. See [the current trust model](TRUSTED_UI.md).


This is an implementation-author assessment, not independent security review. Protect recovery entropy/phrase, BIP39 passphrase/seed, derived keys, storage password/key and exact payment authorization. Address associations, journal and RPC credentials are privacy-sensitive too. A single recovery root shares compromise scope across every chain.

Only wallet-signer creates/imports/decrypts the root, derives signing keys and stores vault encryption keys. By explicit owner instruction (2026-10-24), all application windows now use Electron. Go sends signer-authored prompts through the inherited coordinator transport to Electron main and a dedicated prompt renderer/preload. Passwords/imported phrases/optional BIP39 passphrases use masked, bounded Electron fields; pending recovery setup displays the phrase in a numbered nonselectable view. The ordinary portfolio renderer/public API receives no secret fields. Entropy, binary seeds, private/extended keys and vault keys never enter Electron. A successful separate recorded-word check in Go persists completion; acknowledgment alone cannot authorize it. Resuming interrupted setup requires app-password reauthentication. The owner-authorized Settings → Wallet backup action (2026-10-27) requires explicit confirmation and the current app password on every view before a separate one-use `recoveryBackup` prompt shows numbered words. It cannot mutate the root, completion, vault generation or journal and exposes no ordinary phrase getter or file export. There is no encrypted portable-backup product operation, generic hash/calldata signing, arbitrary derivation, secret QR or plaintext recovery file. The later owner request permits **Copy phrase** only in the authenticated backup view. Main copies its Go-provided words from the exact live delivered prompt with an argument-free private command; no ordinary renderer or other prompt kind can use it. This deliberately expands exposure to the system clipboard and clipboard history. Other apps/managers may retain the words after closing or locking; the wallet claims no automatic or guaranteed erasure.

This expands the trusted secret path: Electron main, the dedicated prompt renderer/preload, Chromium/IPC and the Go coordinator/supervisor transient relay can hold passwords or phrase text. The supervisor validates prompt/reply schemas and the coordinator forwards bounded frames without using credentials for derivation or persistence; that is not an assurance that its memory never contains secrets. Compromise of these trusted components can steal prompted inputs or spoof payment/receive details. Generating a phrase in Go does not preserve the former Go-only display boundary. Best-effort clearing of Go buffers, prompt fields/DOM and main references does not guarantee erasure of immutable Go/V8 strings, serialized frames, display/IPC buffers or library copies. No memory-locking guarantee is claimed. The signer and newly protected coordinator set and self-check RLIMIT_CORE soft/hard zero and PR_SET_DUMPABLE=0 before processing secrets. Coordinator subprocess tests verify failure closure and preserved loopback networking. Electron inherits a zero core-size limit from the launcher, but exec can reset dumpability; post-exec Electron non-dumpability is not guaranteed. A system-managed piped core handler can ignore RLIMIT_CORE. Privileged host crash collection and extraction therefore remain a limitation, not a passed erasure/dump-protection claim. Production binaries omit automation tags and test hooks; retained GTK code/tests are absent from the shipped command dependency graph and do not certify the new UI.

The launcher verifies fixed child binary hashes, starts the public network coordinator over anonymous inherited pipes, then installs Linux no-new-privileges and TSYNC seccomp before execing Electron. The secret child separately installs the same filter. New AF_INET/AF_INET6/AF_PACKET sockets/socketpairs and io_uring setup/entry/registration are denied, including across existing Go threads and later Electron descendants. Unix-domain sockets remain available for display/session services. This is IP isolation, not a complete syscall/filesystem sandbox. The core has network access and RPC credentials while unlocked, and does not derive/store the recovery root. Its private prompt relay transiently carries credential/phrase bytes, so the network-enabled coordinator is part of that input-transport trust boundary. Such data must never enter RPC requests, persistent caches or logs. Lock cancels its contexts and drops references to configured credential-bearing adapters. Already-running library/string copies can outlive those references.

Electron uses sandboxed renderers, context isolation, no Node integration, no webviews or devtools, restrictive local-only protocol/CSP, denied permissions/popups/navigation/downloads, and exact-field typed bridges. The ordinary portfolio at `wallet://app/` exposes only public-data operations. Each dedicated modal at `wallet://prompt/` uses its own minimal preload and a fresh nonpersistent session partition. It receives one signer-created prompt and may send one exact matching reply; its preload has no portfolio, generic IPC, filesystem or remote-resource API. Application code never uses browser storage; the nonpersistent session is cleared at teardown. Main binds each call to the exact live window/main frame, pending request/session/generation and one-use prompt ID. Receive copying uses main's Go-provided address, without a renderer argument. These restrictions separate ordinary portfolio compromise from the secret prompt, but do not protect against a compromised Electron main or trusted prompt renderer. Packaged fuses disable RunAsNode, NODE_OPTIONS and CLI inspection and require ASAR. Linux ASAR loading and local SHA manifests do not authenticate the publisher against replacement of all files. There is no signed updater. Component tests exercise production main/preload/renderer code using Electron doubles; they do not prove Chromium or every display server safe.

Framed IPC is versioned, bounded, strict JSON, duplicate-key checked, correlated to request/method/session/generation and bound to inherited pipes. There is no localhost listener. Top-level null/scalar argument objects are denied. Passwords/phrases travel only in the current validated signer-authored prompt and its scoped credential reply. The private Go channel also carries encrypted-vault RPC settings and narrowly typed exchange authentication capabilities/beneficiary records needed by the network coordinator; these are unavailable through the ordinary portfolio bridge. Public snapshots/responses remain secret-free. Unknown prompt kinds/fields, unsolicited or duplicate prompts, delivery/reply replay and stale generations fail closed. Only value-free rate-limited real-input activity can refresh inactivity during a pending prompt. A stale response or queued request cannot cross lock epochs, start a new secret child, restore old RPC settings or repopulate the ordinary UI. Main references, prompt fields/DOM and ordinary renderer caches clear on cancellation/lock/error and status polling never marks activity.

Lock's coordinator mutex serializes epoch change, context cancellation and child generation invalidation/kill. Signer termination prevents further signing and releases its process state; Electron prompt destruction and reference clearing reduce additional secret lifetime without guaranteeing erasure of Chromium/main/runtime copies. Five-minute inactivity uses real key/button events, not redraws or programmatic fills. OS screen-lock/suspend/shutdown events request lock, parent failure uses parent-death SIGKILL, and pipe EOF terminates the signer. Current UI/protocol/packaged results require separate source-bound evidence; old GTK results do not recertify the changed Electron secret path. Real stock OS logout/suspend/Wayland acceptance remains NOT_RUN. A compromised ordinary renderer can spam public activity, deny service, request dedicated dialogs or misrepresent public data. It has no access to the separate prompt API and cannot manufacture its scoped reply. A compromised trusted prompt/main, compositor, same-user malware or OS can capture inputs or spoof that surface.

Transfer plans bind network/profile, recipient, exact atomic amount, asset identity, fee/reserve, nonce/sequence, expiry, memo, all inputs/outputs and canonical payload. Each secure adapter independently decodes/reconstructs the allowlisted transfer and verifies its produced signature. Dedicated Electron approval of Go-authored details and per-send password verification in Go are mandatory. Plans/reservations persist before approval, signed bytes before broadcast. Unknown submission outcomes retain reservations and reconcile the original identity. Explicit cancellation releases only unsigned PREPARED state. There is no arbitrary message signing. Rollup/TON/NEAR fee estimates are labeled honestly where the protocol cannot enforce a signed total charge cap.

The live vault encrypts root, recovery descriptors, associations, RPC credentials and durable journal together with bounded Argon2id and authenticated XChaCha20-Poly1305. Copying a locked vault permits offline password guessing; choose a strong unique password. Headers permit only bounded reviewed KDF parameters. Atomic no-follow private file operations and single-writer flock defend accidental/malicious filesystem substitution within the stated owner checks. They do not defeat root, hostile filesystem/kernel, storage failure or rollback of an entire valid old directory. In particular, replacing a confirmed profile with older valid pending ciphertext can make recovery completion eligible again after password authentication; recovery completion is authenticated local state rather than an external monotonic record. The separate backup display is deliberately available after confirmation/password verification for the current confirmed vault; it cannot reset completion. Recording the phrase replaces portable encrypted-file backup verification. It restores canonical key derivation, while local journal, account/association/discovery metadata and credentials need independent reconstruction or reconciliation. The three-word check cannot prove that the complete offline copy will remain safe or legible. See [VAULT_FORMAT.md](VAULT_FORMAT.md) and [RECOVERY.md](RECOVERY.md).

RPCs can lie, correlate public addresses, censor, time out or omit history. Network/genesis/code/authority checks prevent known wrong-domain substitutions, but are not consensus proofs. TLS endpoints or explicit loopback nodes are required, redirects/response sizes/nesting/timeouts are bounded, and credentials remain encrypted at rest. Decred uses a verified-network authenticated trusted dcrd scan, not SPV. TON trusts TON Center-compatible data and verifies decoded transaction effects within bounded queries, not independent finality proofs. Every history view shows its finite scope; an incomplete scan is not a confirmed zero. Wallet creation, phrase recovery and ordinary chain transfers require no custodial service. The separately requested optional Exchange feature uses Bybit custody as described below. Analytics, remote scripts/fonts and a fiat-price oracle remain absent.

The owner's later Exchange instruction explicitly extends the original v1 exclusions to include Bybit spot trading and canonical Ethereum USDT. It does not add margin, derivatives, borrowing, exchange agents, arbitrary messages, bridging or arbitrary token discovery. Depositing transfers control of those assets to Bybit. Availability, account restrictions, execution, withdrawal approval, exchange solvency and custody then depend on Bybit. The app cannot guarantee return of deposited assets, a USDT/USD peg or a quoted execution price. Ethereum USDT is the exact registered ERC-20 contract, not a ticker-selected token; its issuer retains its contract's administrative powers, including address restrictions. Token identity/code checks do not remove issuer or custody risk.

Bybit credentials enter only through the masked isolated Electron prompt and are encrypted with the wallet vault. After that transient transport, the API secret stays in the Go signer. The network-enabled core receives only the API key and exact request HMAC needed for its HTTPS headers. The ordinary portfolio receives neither the complete API key nor its secret, private request payloads or beneficiary records. Go restricts authentication to fixed production endpoints, closed GET schemas and the three supported POST schemas. Spot orders explicitly disable leverage and specify quote spending for buys/base spending for sells; internal Funding/Unified transfers and withdrawals each have their own Go-authored approval and app-password check. Withdrawals bind the current owned account address, exact registered network/asset and service-reported route/contract; ambiguous routes and missing required TON deposit memos fail closed. An unavailable exchange route leaves the ordinary blockchain wallet available.

The coordinator is trusted to send the exact approved request and interpret Bybit's authenticated responses. Bybit's [V5 HMAC formula](https://bybit-exchange.github.io/docs/v5/guide) signs the timestamp, API key, receive window and payload; it does not cryptographically bind the HTTP method, endpoint or path. The signer's closed request policy plus the fixed Go client constrain those values locally, but they are not a protocol guarantee against a compromised coordinator. Endpoint labels and TLS authenticate the chosen service connection, not exchange honesty or independent blockchain consensus. The client disables environment proxies, redirects and automatic POST replay, bounds responses and returns fixed numeric error categories rather than provider text that may echo personal data.

Exchange approval is tied to the canonical durable request and a one-use signer-session capability. The signer persists `SUBMITTING` before releasing any POST HMAC; lock/restart invalidates unsigned approvals while retaining uncertain submitted records. Lost responses, rate limits, duplicates and missing execution/fee evidence remain unresolved. They block new exchange writes instead of creating replacement IDs. The four documented first-request parameter/authentication/permission rejection codes have a narrow durable-failure path. A missing withdrawal acknowledgement cannot be safely reconstructed from amount/address because the records API does not query `requestId`. A restored phrase does not restore this journal or exchange credentials. Whole-vault rollback and deletion therefore retain the existing recovery limits; consult the exchange before replacing an uncertain operation.

Exchange acknowledgements are not executions. Spot reconciliation requires matching original order identity/terms and bounded complete execution pages, including separately reported regional taxes; missing/null/unknown fees are not zero. The approval's trading-fee estimate uses the observed taker rate; it is not a cryptographic fee cap and may exclude additional regional taxes. Bybit determines its actual fees/taxes after acceptance. Reconciliation includes supported reported taxes, while additional fee currencies or responses outside the implemented bounded schemas remain unknown instead of being silently omitted. Internal transfers require matching successful transfer records and a fresh target balance before the next step. An on-chain deposit submission does not establish Bybit credit. A withdrawal marked `EXCHANGE_COMPLETED` means Bybit reported completion of the exact remote record; the app does not claim independently verified destination credit or finality. Exchange prices and balances remain service observations. Decimal formatting and scaled fee/aggregate arithmetic refuse amounts beyond the supported uint256 domain; an overflow does not become a reported zero.

For `api.bybit.ae`, personal self-owned withdrawals collect documented beneficiary address/birth fields in dedicated masked prompts. Go shows exactly which personal data will be sent to that endpoint. Those fields persist only inside the encrypted local operation payload and its encrypted prior generations. The private coordinator necessarily handles them for that approved request; ordinary public IPC, logs, browser storage, clipboard and QR exclude them. No UAE schema is guessed from the newer questionnaire page, which does not document that zone. Required TR/KZ/EU/ID forms remain unsupported and those withdrawal paths are refused. Actual regional account/API acceptance, live deposit/trade/withdrawal roundtrips and an independent review of this new boundary remain separate production gates. Implementation-author review and local synthetic tests are not independent audit evidence.

Tested defenses and residual gates are listed in [STATUS.md](STATUS.md), [COVERAGE.md](COVERAGE.md), [STRESS.md](STRESS.md) and the chain evidence files. Synthetic-canary absence applies only to the exercised paths and encodings. Full live-memory extraction, physical attacks, kernel/root control, signer/library supply-chain replacement, hostile X11/Wayland/input methods/accessibility/compositor and same-user capture/injection are outside the software wallet's protection claim. Independent review of the vault, GUI/IPC boundary, all adapters and build chain remains mandatory before production use.

Mainnet is the default process profile; an explicit `--profile=testnet` selects the separate developer vault. The launcher consumes this option and binds it to the coordinator/signer; renderer requests cannot switch profiles. Existing vaults are neither copied nor reclassified. Receive/copy, preparation and signing require completed recovery setup on both profiles, enforced in Go rather than by disabled frontend controls. Signing rechecks eligibility before approval, after confirmation and after password reauthentication. A legacy verified-backup flag alone grants no authority. Account/RPC/password changes do not require recording the unchanged phrase again. A completed setup cannot be reset through public IPC to turn the completion action into a later reveal endpoint.

The mainnet provider defaults and read-only identity checks are documented in [MAINNET.md](MAINNET.md). Decred requires explicitly configured authenticated TLS access; an unconfigured or incomplete scan is unavailable, never a confirmed zero. Credential-bearing endpoint paths/queries are retained only in encrypted settings and Go networking; public network metadata exposes origins only. TON Center requests without an API key are paced locally, with context cancellation and no automatic request/broadcast retry. Public-provider quotas, hostile providers and independent production acceptance remain separate limitations.
