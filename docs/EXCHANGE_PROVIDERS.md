# Exchange providers

The Exchange selector chooses Bybit, Binance or KuCoin. Settings → Exchange stores each service's credentials separately inside the existing encrypted wallet vault. Selecting a service changes the active connection; it does not transfer or exchange assets. Existing Bybit credentials and operation identities remain compatible. A pending or ambiguous funds operation prevents switching providers until its original result is reconciled.

Connection uses the already unlocked, recovery-confirmed session and masked wallet input. Binance and Bybit require the API key and its matching secret. KuCoin additionally requires the API passphrase chosen when creating the key and its API key version, **2 or 3**, as shown by KuCoin. The API passphrase is distinct from the wallet storage password and BIP39 passphrase. Connecting does not ask for the app password again; funds operations and disconnect retain their separate password checks.

Only reviewed, exact production HTTPS endpoints are accepted. The new providers initially support `https://api.binance.com` and `https://api.kucoin.com`; these are the global services. Binance.US, other Binance entities, KuCoin regional services, arbitrary URLs and futures endpoints are not interchangeable and are not silently selected. Existing documented Bybit regions remain available. Account eligibility and the service's regional requirements still apply.

## Authorization and credentials

The trusted Wails UI handles entered credentials transiently. Go signer owns their encrypted persistence; ordinary public status contains only provider, endpoint, connection state and a masked key suffix. Plaintext API secrets, KuCoin API passphrases, wallet passwords and wallet recovery/signing secrets are never put in network requests or reports. KuCoin's required authentication header contains the HMAC-derived API passphrase, not its plaintext value. The network core necessarily handles the service API key and short-lived request authorization.

Each write is separately approved using backend-authored provider, endpoint, owned wallet, exact asset/network, amount, fees and original operation ID. The current app password is checked for that operation. The signer reconstructs the provider's exact native method/path/payload from the immutable encrypted operation. It durably records SUBMITTING before releasing one write authorization. A changed service, payload, price, quantity, destination, chain, credential or expired approval is rejected. Lock clears credential buffers and in-memory approvals; restart never renews a write approval.

The official [Binance authentication specification](https://developers.binance.com/en/docs/products/spot/rest-api) signs the canonical parameter string. Its HMAC does not bind HTTP path or hostname; the network core is trusted to use the locally approved descriptor. [KuCoin authentication](https://www.kucoin.com/docs-new/authentication) binds timestamp, method, path/query and exact body, and separately derives the passphrase header. Fixed endpoint policy still matters because the hostname is outside that HMAC. HTTP clients reject redirects and ambient proxies/cookies, validate TLS, bound bodies and timeouts, and expose value-free errors rather than raw provider messages.

## Deposit, spot and withdrawal

Deposit follows the existing on-chain wallet preparation, current-password confirmation, signing and crash-safe journal. The selected exchange's full chain metadata must match the wallet network and exact token contract; a shared EVM address, ticker or contract suffix cannot establish a new provider route. The returned address is validated by the selected blockchain adapter. TON's required deposit memo is included in the signed payment. A chain receipt does not prove exchange credit.

Bybit retains its existing bounded unleveraged Market workflow. Binance uses **LIMIT IOC** spot orders: a fixed native limit price incorporates the selected slippage, with the exact base quantity and original spending ceiling shown for approval. Any unfilled remainder is cancelled immediately. Buys round quantity down to the provider's increment; limit-price rounding preserves the approved worst price. No margin, borrowing, futures, generic orders or account-mode changes are authorized. Only the selected pinned wallet asset's USDT or USDC pair is eligible; quote-currency selection does not create a new on-chain token policy.

**KuCoin spot trading is BLOCKED by its current fee contract.** [KuCoin documents](https://www.kucoin.com/support/30380295503769) that KCS fees can debit Funding, Trading or staked KCS, while spot trade history can still show the original quote-currency fee. The reviewed Classic APIs do not provide a safe read-only proof that those additional debits are disabled. The app therefore displays the limitation, rejects new swap preparation and approval in the signer, and releases no trade signature. Native IOC encoders and read-only original-order reconciliation do not enable trading. A manual claim that KCS payment is disabled cannot override this gate.

Binance Funding/Spot transfers remain separate operations with their own approval and durable identity. KuCoin uses its **Classic** Funding/Spot accounts and checks account mode before money-moving actions; a Unified Trading Account requires a separate implementation and is rejected explicitly. KuCoin's reviewed transfer API returns an acknowledgement without an exact Classic transfer-status lookup, so new automatic internal transfers are blocked. Move the required amount to Funding through KuCoin itself before requesting a wallet withdrawal; an insufficient Funding balance produces manual-funding guidance without any write. Previously acknowledged ambiguous transfers retain their identity and remain unresolved. The app never changes the user's account mode. The [KuCoin account-mode API](https://www.kucoin.com/docs-new/v2/rest/ua/get-account-mode) distinguishes those domains.

Withdrawals target only the selected owned wallet on its exact verified chain. Provider questionnaires and restrictions must be checked before funding transfers. Binance's ordinary capital endpoint is used only when its documented questionnaire requirement is exactly NIL; an unsupported regional questionnaire blocks the action. Bybit retains its existing explicit regional questionnaire gates and UAE data handling. A provider response, missing field or ambiguous network never bypasses these checks.

Fee contracts are provider-specific. Bybit retains `feeType=1` and its inclusive debit. Binance preserves the exact API `amount` without inventing a guaranteed gross/net interpretation; its estimated fee is displayed and reserved separately. KuCoin explicitly selects external fee deduction. These services control actual charges and recipient credit; estimates are not promises of on-chain finality or a provider-enforced fee ceiling. See the official [Binance capital API](https://developers.binance.com/en/docs/catalog/core-trading-wallet/api/rest-api/capital) and [KuCoin withdrawal API](https://www.kucoin.com/docs-new/rest/account-info/withdrawals/withdraw-v3).

Additional fee assets require explicit support. Binance BNB fee payment is checked before trading; an unsupported third-asset fee configuration blocks that trade. KuCoin's unobservable additional KCS fee setting blocks every new spot trade. Unexpected fee currencies, incomplete fill pages, tax data or mismatched totals keep original-operation reconciliation unresolved. Deposit and withdrawal remain separate capabilities.

## Recovery and evidence

Operation identity is preserved through ambiguous acknowledgements, lock, process exit and reload. There is no automatic replacement or automatic retry of a state-changing exchange request. Reconciliation uses exact original client order IDs and acknowledged server IDs, never amount/address/time resemblance. Binance withdrawal recovery may query its exact original `withdrawOrderId`; it still requires a single matching record and the complete owned network/destination identity. The query supplies a bounded historical interval around the original authenticated request timestamp, avoiding the API's default last-seven-days window after restart. Binance internal transfers have no client transfer ID, so only an acknowledged server transfer ID permits reconciliation. KuCoin withdrawal remarks are not treated as a safe client-ID lookup. Some services expose fewer lookup fields; missing proof remains UNKNOWN and blocks conflicting writes. A completed withdrawal is the exchange's observation, not independent proof of recipient-chain credit.

Binance's original-request adapter also conservatively requires the reported amount to equal the exact submitted API amount. This is an acceptance restriction, not evidence of gross/net semantics: a service record using another amount convention remains UNKNOWN despite matching IDs, and never authorizes a replacement.

The recovery phrase restores wallet keys, not exchange keys, API passphrases, service access or the local remote-operation journal. Preserve the encrypted local profile for those records. Connecting another provider does not replace or merge an unresolved operation.

Local implementation tests use public synthetic credentials, independent HMAC expectations, real owned HTTP/TLS fixtures and disposable encrypted profiles. They establish local protocol and state-machine behavior, not account eligibility or successful real trades. Private authentication against real service accounts, funded deposit → spot fill → owned-wallet withdrawal, regional account matrices and independent review are **NOT_RUN**. No real credentials or automatic mainnet funds are used to produce local evidence. The current implementation/test checklist is maintained in [STATUS.md](STATUS.md).

Reproduce the local checks from the repository root:

```sh
go test ./internal/exchange/... ./internal/signer ./internal/vault ./internal/walletsigner ./internal/walletcore
go test -race ./internal/exchange/... ./internal/signer ./internal/vault ./internal/walletsigner ./internal/walletcore
go vet ./internal/exchange/... ./internal/signer ./internal/vault ./internal/walletsigner ./internal/walletcore
python3 internal/exchange/test-native-mutations-test.py
python3 internal/exchange/test-native-mutations.py
```

The six native mutation controls use isolated source snapshots and Go overlays. A mutant counts as killed only when its designated runtime assertion fails; a build failure, unrelated failure, panic, skipped test or timeout is invalid evidence. The report records its exact source hashes. These controls cover exact native wire authorization, required operation approval, the original IOC spending ceiling, input-currency fees, API-passphrase clearing and execution-price bounds. KuCoin input-fee checks concern retained historical observations and pure amount policy; they do not establish or enable the blocked new-trade capability.
