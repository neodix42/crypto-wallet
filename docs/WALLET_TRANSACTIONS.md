# Wallet transaction history

Each selected wallet has a transaction table with date/time, source, destination, amount, explorer link, comment and status. It combines that owned account's local outgoing journal across native currency and all token assets with bounded chain observations. Switching the Send asset does not narrow the wallet table. One transaction may contain several effect rows, retaining the exact token identity and precision of each effect. Unknown peers, dates or comments remain unknown; the UI does not extract them from provider prose.

Amounts use atomic integers and the asset's registered decimals, never floating-point arithmetic. Go supplies structured public effects and fixed explorer routes. Explorer links cannot navigate to URLs supplied by an RPC/indexer. Local development networks without a reviewed public explorer have no link. Plaintext comments are rendered as inert text. Chain timestamps are converted to Unix seconds; local operations use their persisted preparation time. Older journal entries without `createdAt` keep an unknown local date instead of inventing a historical time.

Local journal entries describe approved attempts and their original signed transaction identity. Chain observations can show incoming or externally initiated transfers within the limits below. They never release an UNKNOWN operation's reservation, reconcile a journal by an amount/address heuristic, or authorize another signature. Displaying a failed attempt's amount does not establish a completed transfer. Restoring a recovery phrase reconstructs keys; it cannot restore local comments/journal records or prove an exhaustive chain history.

## Exact observation scopes

| Network family | Native and token interpretation | Bound and remaining unknowns |
| --- | --- | --- |
| Ethereum, Base, HyperEVM | Direct native value transactions and standard ERC-20 `Transfer` logs for every pinned or explicitly tracked contract. Native and token effects sharing a transaction hash are merged, with distinct effect identities. Metadata/code policy and receipt/inclusion checks remain required. | Latest 128 blocks, at most 4,096 observed transfer records before merging. Internal native calls, older activity and untracked tokens remain outside this scan. Pending observations are distinguished from finality; reverted execution cannot establish a successful token event. |
| NEAR | Direct transactions with exactly one native `Transfer` action. Standard `nep141` v1.0.0 `ft_transfer`, `ft_mint` and `ft_burn` events from approved token executors, with owned peers/owner and exact u128 amounts. Mint/burn rows identify their event in the comment and keep the absent source/destination unknown. Token events may appear in nested receipts even when the transaction called another contract. | Latest 12 final blocks for direct calls, plus the latest 25 account FT candidates from NearBlocks. At most 4,096 scanned transaction records, 128 receipt outcomes and 1,000 effects per token transaction. | HyperCore | Provider-observed HYPE spot-transfer ledger entries, with separate source/destination and exact HYPE precision. | Fixed latest-30-day window with bounded inclusive timestamp pagination and page commitments. | Aptos | Recognized direct APT entry functions: `aptos_account::transfer`, and the existing exact native-coin forms of `aptos_account::transfer_coins`/`coin::transfer`. | Latest 256 committed ledger versions. Other functions, internal effects and other token standards are outside the scan. |
| Decred | Already authenticated and locally decoded dcrd blocks. Relevant native DCR output effects retain individual output identities. | TON | Linked archival transaction BOCs, native inbound/outbound internal messages and bounded standard plaintext message comments. Multiple native messages remain distinct. | Pages of at most 100 transactions, 256 messages per transaction and 1,000 outgoing messages per page. These families cover all eight active mainnet networks and their supported development profiles. Additional imported-token history applies to the existing Ethereum/Base ERC-20 and NEAR NEP-141 policies; this change does not introduce a new token signing standard. Failed EVM token identity/code/precision checks skip that token's history with the exact unavailable asset IDs disclosed in the scope, preserving checked native and other healthy token rows. NEAR indexer transport/HTTP failures retain already checked native and direct-token-call rows with an explicit unavailable/incomplete scope and `complete:false`. Malformed candidate/event data or forged receipt bindings fail closed. None of these states becomes verified empty history.

## NEAR indexer trust boundary

The wallet requests `/v3/accounts/{owned-account}/ft-txns?limit=25` from the fixed selected-network NearBlocks service. Candidate account, contract, transaction hash and receipt identity are checked. A separate transaction lookup supplies only a candidate signer for the final RPC query. Provider quantities, metadata, status, timestamps and links do not establish the displayed effect. Duplicate candidates do not duplicate effects. Every claimed tracked receipt must have an exact matching owned event in the final RPC receipt graph; missing descendants, cycles, failed receipts, mismatched transaction/signers/executors and delayed transaction binding remain unavailable. The shared receipt checker also rejects cycles for staking/token reconciliation, leaving those journal operations unresolved. Tracked token policies are checked through the selected chain's final RPC state. An untracked contract is never imported by history discovery.

The NearBlocks API service is an additional read-only provider and receives the public owned account address. It can be incomplete, delayed, rate limited or unavailable. The production Go `chainutil.Client` and curl public-account probes returned HTTP 200 with the documented 25-candidate envelope; a Python transport probe returned HTTP 403. These read-only observations establish neither reliable future availability nor final RPC receipt acceptance for a live owned account, which remains **NOT_RUN**. Typed-schema/hostile-provider fixtures pass locally. Availability failures preserve direct RPC rows with an explicit partial scope; they do not turn an unavailable indexed snapshot into a complete history claim. Attribution: powered by Nearblocks.io APIs.

The reviewed NearBlocks [FT response schema](https://github.com/Nearblocks/nearblocks/blob/7cbb64eedadee0011ea3cb7a90040003f8bb1c1d/packages/nb-schemas/src/accounts/fts/response.ts) and [v3 account FT route](https://github.com/Nearblocks/nearblocks/blob/7cbb64eedadee0011ea3cb7a90040003f8bb1c1d/apps/api/src/routes/v3/accounts/fts.ts) are pinned to commit `7cbb64eedadee0011ea3cb7a90040003f8bb1c1d`. The event interpretation follows the primary [NEP-297 envelope](https://github.com/near/NEPs/blob/master/neps/nep-0297.md) and [NEP-300 fungible-token transfer event](https://github.com/near/NEPs/blob/master/neps/nep-0300.md), reviewed 2026-10-30.

## Provider contracts and pagination

The implementation uses documented [EVM JSON-RPC block/receipt/log methods](https://ethereum.org/developers/docs/apis/json-rpc/) and the standard [ERC-20 transfer event](https://eips.ethereum.org/EIPS/eip-20). HyperCore's provider window and inclusive pagination use the official [Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint). Aptos history uses committed transaction responses from the primary [Aptos API types](https://github.com/aptos-labs/aptos-core/blob/main/api/types/src/transaction.rs). Decred continues to use its authenticated [dcrd RPC contract](https://github.com/decred/dcrd/blob/master/docs/json_rpc_api.mediawiki). TON archival continuation follows the [TON Center implementation](https://github.com/toncenter/ton-http-api/blob/master/ton-http-api/pyTON/main.py). These references were rechecked on 2026-10-30; they describe provider contracts, not a guarantee of complete or consensus-authenticated history.

The public transport carries at most 128 transactions and 256 KiB per page, with single-use session/account/revision-bound cursors. Decred's optional legacy report appears on the first page only if that full envelope fits; otherwise structured entries continue normally and the scope discloses report omission. All common memory, identity and cursor limits remain in [the pagination contract](HISTORY_PAGINATION.md).

The native controller keeps at most 16 account caches, with at most 2,048 transactions and 4 MiB for each account's chain/local stream, and shows 128 transfer rows at a time. Starting another wallet action pauses an automatic chain scan cooperatively, leaving the unlocked signer and local payment journal intact; Refresh history can restart that observation. Cancellation binds the original read-only request and cannot cancel signing, a payment, another network operation or another session.
