# Wallet transaction history

Each selected wallet has a transaction table with date/time, source, destination, amount, explorer link, comment and status. It combines that owned account's local outgoing journal across native currency and all token assets with bounded chain observations. Switching the Send asset does not narrow the wallet table. One transaction may contain several effect rows, retaining the exact token identity and precision of each effect. Unknown peers, dates or comments remain unknown; the UI does not extract them from provider prose.

Amounts use atomic integers and the asset's registered decimals, never floating-point arithmetic. Go supplies structured public effects and fixed explorer routes. Explorer links cannot navigate to URLs supplied by an RPC/indexer. Local development networks without a reviewed public explorer have no link. Plaintext comments are rendered as inert text. Chain timestamps are converted to Unix seconds; local operations use their persisted preparation time. Older journal entries without `createdAt` keep an unknown local date instead of inventing a historical time.

Local journal entries describe approved attempts and their original signed transaction identity. Chain observations can show incoming or externally initiated transfers within the limits below. They never release an UNKNOWN operation's reservation, reconcile a journal by an amount/address heuristic, or authorize another signature. Displaying a failed attempt's amount does not establish a completed transfer. Restoring a recovery phrase reconstructs keys; it cannot restore local comments/journal records or prove an exhaustive chain history.

These families cover all eight active mainnet networks and their supported development profiles. Additional imported-token history applies to the existing Ethereum/Base ERC-20 and NEAR NEP-141 policies; this change does not introduce a new token signing standard. Failed EVM token identity/code/precision checks skip that token's history with the unavailable asset IDs disclosed in the scope, preserving checked native and healthy token rows. NEAR can retain separately checked rows while disclosing unavailable candidate streams or archival execution, always with `complete:false`. Malformed candidate/event data or forged receipt bindings fail closed. None of these states becomes verified empty history.

## Ethereum, Base and Aptos index/archival services

Ethereum mainnet uses the keyless Routescan account API, with Blockscout as an availability fallback. Base and Sepolia use the fixed network-specific Blockscout account API. If the public index is unavailable, an already configured Alchemy-compatible RPC can supply incoming/outgoing `alchemy_getAssetTransfers` candidates and opaque continuations. The fallback reuses the existing encrypted trusted-RPC configuration; it adds no credential field, bundled demo key or exchange-key access. Keep credentials out of commands, screenshots, issues and logs. A scan cannot silently switch from a paginated index into a recent-block empty result. Blockscout is changing its public API offering; default Base requests returned Cloudflare HTTP 403 in this environment on 2026-10-30, while ordinary Base RPC remained available but did not implement this address index. This live provider gate is **BLOCKED**; open the Base wallet's **Configure trusted RPC** control for a working compatible endpoint, or retry the public index. Scripted provider tests establish fallback behavior, not public Base acceptance.

Aptos uses the fixed official AptosLabs GraphQL `account_transactions` table, including incoming impacted-account activity. The index supplies only versions. The selected REST node checks chain/current authority and each committed transaction; HTTP 410 pruning can fall back only to `archive.mainnet.aptoslabs.com/v1` or the testnet equivalent, independently checked for chain and ledger height. An index error, archival error or mismatched version remains unavailable. The index, archive and RPC operators learn the queried public address or transaction positions; they can omit activity and are not consensus proofs.

## NEAR indexer trust boundary

The wallet pages `/v3/accounts/{owned-account}/txns`, `/receipts` and `/ft-txns` from the fixed selected-network NearBlocks service, with `limit=25`, a frozen timestamp upper bound and its bounded opaque `meta.next_page` continuation. The private position binds the owned descriptor, network, RPC/indexer, frozen head and token policies. Candidate account, contract, transaction hash and receipt identity are checked. A separate transaction lookup supplies only a candidate signer when needed. Provider quantities, metadata, status, timestamps and links do not establish the displayed effect. Every candidate produces a source-independent whole-transaction observation so native, receipt and FT streams can overlap without duplicating transfers.

Native receipt payloads are fetched separately with `EXPERIMENTAL_receipt` and bound to the checked final execution graph, receipt executor and frozen execution-block bounds. Root actions appear once, protocol `system` refunds are excluded and unsuccessful child effects are never credited. Every claimed tracked FT receipt needs an exact matching owned event in that graph. Missing descendants, cycles, mismatched transaction/signers/executors and delayed transaction binding remain unavailable; explicit failed attempts retain failed status. The shared receipt checker also rejects cycles for staking/token reconciliation, leaving those journal operations unresolved. Tracked token policies are checked through the selected chain's final state; history never imports an untracked contract.

The NearBlocks API service receives the public owned account address and can be incomplete, delayed, rate limited or unavailable. Missing candidate streams or historical RPC evidence stay explicit and incomplete, even when separately checked rows remain usable. They never become a complete empty history claim. Public read-only provider checks and controlled schema/receipt regressions are recorded in the current checklist; they do not establish reliable future availability or exhaustive archival recovery. Attribution: powered by Nearblocks.io APIs.

For exact built-in `near.org`/FastNear public RPC configurations, historical read-only evidence uses the fixed selected-network [FastNear archive](https://docs.fastnear.com/rpc), checked for chain identity and the same frozen head hash, height and nanoseconds. Custom/local RPCs are never bypassed. Sending/signing endpoints stay unchanged. The [official endpoint deprecation notice](https://www.near.org/blog/deprecation-of-near-org-and-pagoda-co-rpc-endpoints) explains why the previous default cannot be relied on for old records. The archive learns public transaction/receipt identities and can still be unavailable. Ethereum/Base and NEAR token policies are checked at the frozen current head, rather than certifying metadata/runtime at every historical event block; historical upgrades or precision changes remain outside this evidence.

The reviewed NearBlocks [FT response schema](https://github.com/Nearblocks/nearblocks/blob/7cbb64eedadee0011ea3cb7a90040003f8bb1c1d/packages/nb-schemas/src/accounts/fts/response.ts) and [v3 account FT route](https://github.com/Nearblocks/nearblocks/blob/7cbb64eedadee0011ea3cb7a90040003f8bb1c1d/apps/api/src/routes/v3/accounts/fts.ts) are pinned to commit `7cbb64eedadee0011ea3cb7a90040003f8bb1c1d`. The event interpretation follows the primary [NEP-297 envelope](https://github.com/near/NEPs/blob/master/neps/nep-0297.md) and [NEP-300 fungible-token transfer event](https://github.com/near/NEPs/blob/master/neps/nep-0300.md), reviewed 2026-10-30.

## Provider contracts and pagination

The implementation uses documented [EVM JSON-RPC block/receipt/log methods](https://ethereum.org/developers/docs/apis/json-rpc/) and the standard [ERC-20 transfer event](https://eips.ethereum.org/EIPS/eip-20). Candidate contracts follow [Routescan accounts](https://docs.routescan.io/api/etherscan/accounts), [Blockscout accounts](https://docs.blockscout.com/devs/apis/rpc/account) and the configured-RPC [Alchemy transfer API](https://www.alchemy.com/docs/data/transfers-api/transfers-endpoints/alchemy-get-asset-transfers). HyperCore uses the official [Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint). Aptos uses [committed API transaction types](https://github.com/aptos-labs/aptos-core/blob/main/api/types/src/transaction.rs); native event/store interpretation was checked against framework commit [`8fc868b`](https://github.com/aptos-labs/aptos-core/tree/8fc868b2218e795a58a2ddcf8e1522dccb66ba99/aptos-move/framework/aptos-framework/sources), including `primary_fungible_store.move`, `object.move`, `fungible_asset.move` and `coin.move`. Decred retains its authenticated [dcrd RPC contract](https://github.com/decred/dcrd/blob/master/docs/json_rpc_api.mediawiki); TON follows [TON Center archival transactions](https://github.com/toncenter/ton-http-api/blob/master/ton-http-api/pyTON/main.py). These primary references were rechecked on 2026-10-30; they describe provider contracts, not a guarantee of complete or consensus-authenticated history.

The public transport carries at most 128 transactions and 256 KiB per page, with single-use session/account/revision-bound cursors. Decred's optional legacy report appears on the first page only if that full envelope fits; otherwise structured entries continue normally and the scope discloses report omission. All common memory, identity and cursor limits remain in [the pagination contract](HISTORY_PAGINATION.md).

The native controller keeps at most 16 account caches, with at most 2,048 transactions and 4 MiB for each account's chain/local stream, and shows 128 transfer rows at a time. Starting another wallet action pauses an automatic chain scan cooperatively, leaving the unlocked signer and local payment journal intact; Refresh history can restart that observation. Cancellation binds the original read-only request and cannot cancel signing, a payment, another network operation or another session.
