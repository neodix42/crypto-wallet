# TON deployment confirmation and wallet history

The Deploy button opens the exact V5R1 approval dialog in the main window. Confirm its owned address, immutable wallet ID/profile, zero outgoing transfers, fee reserve and current app password. The original subwallet-0 profile remains valid; changing to subwallet 42 would create a different address and does not move its existing balance.

`PREPARED` is an unsigned local operation, not an on-chain deployment. Previously, the UI saved that record but kept its Review button in transient state. After the transient preview was lost, clicking Deploy generated a second plan; the signer correctly rejected the duplicate reservation. This is a UI/state-resumption failure, not evidence that 0.2 GRAM is insufficient.

The corrected core first finds the owned wallet’s existing operation. It returns the exact unexpired unsigned deployment for confirmation without querying RPC or rewriting the record. An explicit Deploy click can durably cancel an expired unsigned deployment before obtaining a fresh state/fee preview. A genuinely fresh signer unlock continues its existing crash policy: unsigned previews become CANCELLED, their original bytes remain recorded, and an explicit Deploy click obtains a new preview; a cancelled preview can never be replayed. Any signed, submitting, submitted or ambiguous operation keeps its original identity and bytes; use **Check status** in that wallet’s history. There is no automatic broadcast/retry or change of funded address.

Settings has Wallet, Exchange and Appearance sections. The separate Journal page is removed. The wallet’s transaction table contains review/cancel/status controls only for matching locally recorded operations; observed chain entries do not grant signing authority. Review of an unsigned operation opens the backend-authored exact confirmation and current-password dialogs. **Broadcast original signed operation** explicitly retransmits bytes that were already approved and signed; it does not ask for a new password, create a replacement or sign again. **Check status** only reconciles the original identity. The encrypted internal ledger remains essential for crash recovery and duplicate-send prevention; an explorer-style history table is only its presentation.
