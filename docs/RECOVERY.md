# Recovery and ordinary use

The recovery phrase is the backup of the wallet's cryptographic root. The app no longer creates, verifies or restores encrypted portable backup files. The live vault remains encrypted. There is no password reset service or hidden master password.

On first launch, choose **Create wallet** and enter a new app password twice in the masked native Go window. It accepts 12–4096 UTF-8 bytes without normalization. Go generates a cryptographically random English BIP39 root: 12 words by default, with a separate advanced 24-word option. A password, a user-written sentence and Electron's random source never supply the entropy.

The Go-owned **Record recovery phrase** window then shows the numbered phrase. Write every word in order and store the copy somewhere private and offline. Anyone who obtains it can derive the wallets. The phrase label cannot be selected or copied, and there is no secret QR, save-file action, Electron phrase field or phrase IPC response. After **I wrote it down**, the phrase disappears and three masked entries ask for words 2, 6 and the final word. Confirming the correct words records completion in the authenticated live vault and enables receive and payment authorization on both profiles. This checks the requested words; it cannot prove the completeness, durability or secrecy of the user's offline copy.

Cancelling either step or entering incorrect words leaves the same encrypted root pending setup. It does not generate a replacement root. Use **Complete recovery setup**, authenticate with the app password and finish recording that phrase. Once setup is confirmed, this action cannot reveal it again for that authenticated vault generation. Replacing the entire profile with older valid pending ciphertext can restore pending status; the wallet has no external anti-rollback authority. Existing vaults from the former backup workflow also require this completion step; their old verified-backup flag does not grant payment authority. Public balances and account listings do not prove recovery setup is complete.

To restore on another installation, start an empty profile on the correct network and choose **Restore from recovery phrase**. Enter the desired app password twice, the complete phrase and any original optional BIP39 passphrase in the masked native Go window. Confirm the recovery-limits notice and compare known public addresses before use. Recovery does not require the old machine, username, OS keyring, application files or storage password. Using the same app password is supported, but a different new app password reproduces the same blockchain wallets too. The app password only encrypts that installation. An optional BIP39 passphrase is a different secret: it changes the derived wallets and must be supplied exactly. New generated wallets use an empty BIP39 passphrase. A passphrase typo can create different valid wallets; an empty or unavailable balance cannot prove which passphrase was intended.

Import accepts valid English BIP39 lengths 12, 15, 18, 21 and 24, with the documented checksum, exact single ASCII word spaces and NFKD rules. It does not translate words or silently repair a phrase. TON uses this application's BIP39/SLIP-0010 Wallet V5R1 profile, rather than a native TON mnemonic. External-wallet acceptance of each phrase length is a separate interoperability claim.

The default profile is mainnet. `./wallet --profile=testnet` opens separate developer data; selecting a profile never migrates or reclassifies a vault. Mainnet is a connection default, not a claim that independent review or production acceptance is complete. Restore into an empty private profile: existing `vault.lwv` or `vault.previous.lwv` prevents creation of a replacement root. An unavailable profile is not treated as empty. Preserve an existing profile separately and use a fresh OS user or private `XDG_CONFIG_HOME` for an isolated destination. That environment variable selects only a data directory, never secret input.

Phrase restoration initially reconstructs this application's canonical index-zero accounts for every supported network in the selected profile. **Recover account indices** derives an explicit inclusive range, at most 20 account groups per request, within indices 0–999999. Repeat deliberate ranges for accounts added later. This is local key derivation, not a statement that all balances or transaction history were searched. Hidden status, labels, RPC credentials/settings, pending-payment journal, named/rotated associations and issued-address discovery counters are installation metadata; the phrase does not encode them. Never assume another installation knows whether a payment was already signed or submitted. Reconcile its original public transaction identity before initiating another payment.

NEAR names, rotated Aptos original-address associations, historical TON contracts and arbitrary third-party paths require separate verified metadata/discovery. The dedicated association operation verifies supported NEAR/Aptos associations in Go. Unsupported schemes or contracts fail closed. HyperCore spot and HyperEVM remain separate balance and receipt domains. A common EVM-format address neither proves Core activation nor transfers funds between ledgers.

For Decred, retain the relevant account indices and discovery bounds separately. Set an appropriate birthday block, address gap (1–100), per-branch address limit (up to 10000), and block scan budget (up to 2000000; 0 selects the default 10000). Discovery uses authenticated trusted dcrd, not SPV. Restore cannot infer old receive/change counters from the words alone. Scan an adequately early range and increase bounds for historical gaps. An incomplete scan is an error, never zero funds. A verified checkpoint establishes only the displayed range; finite history queries on other chains are not exhaustive archival discovery either.

The wallet starts locked after every restart. Unlock uses the native app-password prompt. Each send still requires an immutable exact plan, authoritative Go confirmation and password reauthentication. Inspect the full recipient, actual network, token identity, amount, fee currency/reserve/cap, every Decred output and memo. Base/Horizen, NEAR and TON display estimates/reserves honestly where their protocols cannot enforce a signed total charge cap. Decred's nonzero wire expiry causes ordinary recipient/change outputs to require CoinbaseMaturity before spending: 256 confirmations on mainnet and 16 on testnet3/simnet. Lock cancels ongoing requests and kills the secret-bearing process; it cannot recall a signed or broadcast payment. Unknown outcomes retain the original transaction identity and never automatically create a replacement payment.

Password rotation preserves the phrase, all addresses and recorded recovery completion. A copied older live vault remains decryptable with its old password; changing a local password cannot revoke an already copied secret or vault. The native phrase display deliberately exposes the phrase to the trusted display server and input environment. A compromised OS, compositor, same-user capture tool or malicious accessibility/input service can defeat that local protection. Best-effort widget/buffer clearing is not a guarantee of erasure from every library or display buffer.

Evidence is tracked in [PHRASE_RECOVERY.md](PHRASE_RECOVERY.md). The focused native race test in `reports/phrase-native-focused.log` passed on an owned 1024×768 X11 display using public synthetic 12/24-word vectors. It covers explicit confirmation, cancellation, incorrect/overlong entries, nonselectable phrase labels, clearing before widget destruction, bounded geometry and unchanged clipboard. Those checks do not establish a second physical machine, a clean supported-OS/Wayland matrix, public-network funding or independent security review.
