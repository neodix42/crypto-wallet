# Test plan and release gates

## 1. Purpose, evidence, and identifiers

This plan is mandatory implementation scope. It specifies tests to build, not tests already executed. All seven requested assets must pass their respective gates; HyperCore and HyperEVM are separate HYPE implementations, and Base and current Horizen L3 are separate ZEN implementations. A working Ethereum adapter does not establish compatibility with either HyperCore or another network's token registry.

Use the stable requirement IDs below in test names, issue references, CI reports, and the acceptance matrix. Keep a machine-readable traceability file mapping each ID to positive tests, adversarial tests, fixtures, and execution evidence. Report `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`, or `NOT_APPLICABLE` with a concrete reason. Never convert an unavailable endpoint, absent faucet balance, missing native dependency, or skipped test into a pass.

**TP-001 — Evidence integrity.** Use synthetic test secrets and public vectors only. No real user seed, password, private key, production vault, or funded mainnet signing identity may enter tests, fixtures, snapshots, screenshots, or CI variables. Tests must assert externally meaningful behavior, including rejection paths. Do not invent tests that merely reproduce implementation logic, inflate coverage with trivial assertions, suppress failures, or exclude difficult first-party code to improve percentages.

**TP-002 — Independent oracles.** Freeze reference outputs with generator repository, commit/release, algorithm/profile, input, expected public result, and fixture checksum. Generate expectations with independent upstream implementations or published vectors, not the Go functions under test. Tests may use public synthetic private values internally, but normal reports print public outputs and fixture IDs only. Reference tools must never handle user secrets.

## 2. Coverage and quality gates

**TP-010 — Enforced coverage.** Aim for 100% of meaningful reachable critical logic, with a written review of every uncovered security/funds path. The numbers below are minimum release floors, not a reason to stop adding necessary tests. Measure first-party code; report exclusions and generated/vendor files separately. Apply floors per critical package, not only to an aggregate that can hide an untested adapter.

| Area | Minimum gate |
|---|---|
| Go vault, mnemonic/derivation, signing policy, address/amount validation, transaction construction/serialization, fees/change, and authorization | 95% statement coverage in each critical package |
| Other first-party Go application code | 90% statement coverage |
| Electron main/preload/IPC validation | 95% statements and 90% branches |
| Dedicated secret-bearing Electron prompt logic | 95% statements and 90% branches |
| UI application logic | 90% statements and 85% branches |
| Enumerated security and fund-preservation invariants | 100% mapped to passing positive/negative tests |

Go's standard coverage measures statements, not branches. Do not label it branch coverage. Exercise Go decision outcomes through explicit test cases and mutation testing. A numerical floor never excuses an untested fatal scenario. Test ordinary glue and failure handling where they cross security boundaries.

Owner Exchange amendment (2026-10-24): Bybit credential/authentication, route/amount validation, signing policy and fee reconciliation are critical code under these existing floors. Adding the custodial spot extension or Ethereum USDT does not waive any original wallet network, recovery, secret-handling or release requirement. Local provider fixtures must remain distinguishable from actual API/node/packaged acceptance.

**TP-011 — Mutation gate.** Introduce controlled mutants that remove authentication checks, alter chain IDs, skip AEAD verification, weaken KDF bounds, bypass confirmation, accept changed recipients, misclassify change outputs, permit signing while locked, reuse nonces, or re-sign ambiguous payments. Every enumerated critical mutant must be killed. Document equivalent mutants individually; never blanket-ignore survivors. Run race detection, static analysis, dependency vulnerability review, and type checks; unresolved critical/high findings relevant to deployed code block release.

**TP-012 — Fuzz gate.** Maintain seed corpora for vault headers, IPC frames, BIP39 input, derivation paths, addresses/URIs, decimal amounts, RPC responses, transaction codecs, BOC/cell input, and DCR scripts/outpoints. Require bounded allocations, bounded recursion, timeouts, no panic, no secret-bearing error, and fail-closed results. Run deterministic corpus regression on every change, short time-bounded fuzzing in CI, and longer scheduled campaigns. Every discovered failure becomes a fixed regression case.

## 3. Secret generation, import, and compatibility

**TP-020 — Entropy and BIP39.** Test successful OS CSPRNG operation and injected short-read/failure behavior; failure must never fall back to predictable entropy. Cover 12-word default creation, explicitly versioned 24-word creation, all supported valid import lengths, word-count/checksum failures, unknown words, whitespace policy, NFKD normalization, and word-list selection. Verify complete BIP39 vectors and SLIP-0010/BIP32 vectors, including leading zeros and invalid-child handling. Do not use statistical randomness tests as proof of entropy quality.

**TP-021 — Password separation.** The local app password must never become the BIP39 passphrase. Changing the app password preserves every derived address. An imported nonempty BIP39 passphrase must change derived keys exactly as reference vectors specify. Test Unicode, empty values, long bounded inputs, and accidental trimming/normalization. A valid but different passphrase produces a different wallet; the UI must not invent an ability to detect the intended passphrase.

**TP-022 — Immutable profiles.** Test at least indices 0, 1, and a higher bounded account index for every supported profile. Clean restoration must reproduce all addresses, contract versions, and derivation rules. Dependency upgrades must preserve fixture results. Unsupported external wallet profiles must produce an explicit incompatibility result, never a silent alternate derivation. Test named-account associations, rotated-key accounts, change branches, and TON contract metadata separately from key derivation.

## 4. Vault, phrase restoration and crash recovery

**TP-030 — Authenticated vault.** Test correct/incorrect passwords, fresh randomness, supported versions, and declared KDF/cipher settings. Alter each authenticated header field, salt, nonce, ciphertext, authentication tag, and profile manifest independently; test wrapped keys separately only if the implemented format includes them. Test truncation at structural boundaries, oversized lengths, trailing garbage, duplicate fields, unsupported algorithms, weak or excessive KDF parameters, and malformed encodings. Unlock must release no partial plaintext and must not overwrite the original file on failure.

**TP-031 — Atomic persistence.** Inject failures before/after write, sync, rename, directory sync, and journal checkpoint. Cover disk full, permission changes, interrupted migration, concurrent launch, stale locks, symlink substitution, and process termination. Recovery must produce either the valid previous version or the complete new version. Never silently initialize an empty wallet over an unreadable vault. Check intended directory/file permissions and ensure temporary files contain ciphertext only.

**TP-032 — Password change and phrase recovery.** Restore a generated phrase using an independently copied application and empty HOME/config/vault directories, with no source wallet files or machine keyring copied. Compare all canonical network/profile/account identities, including additional explicit indices. Test the same and a different app password, plus original optional BIP39 passphrase handling. Persist the encrypted root before phrase display, test wrong recorded words, cancellation, restart/resume, storage conflicts and failed acknowledgment persistence. Existing vaults preserve root/addresses and require the new confirmation instead of trusting an old backup flag. Password rotation preserves addresses and recovery confirmation. Phrase-only restore does not recover associations, RPC credentials, discovery counters or local journal; report and test those limitations without inventing metadata.

**TP-033 — Isolated Electron phrase containment.** Owner policy (2026-10-24) authorizes the dedicated Electron prompt, its preload/main and transient Go coordinator prompt transport to handle entered credentials and displayed/imported phrases. The ordinary portfolio/public bridge, diagnostics, logs, arguments/environment, browser storage, plaintext files, QR and network payloads never carry secrets; the only clipboard exception is the later owner-authorized Copy phrase action from the authenticated backup view; entropy, binary seeds and private keys stay in Go and remain undisplayed. Test separate prompt origin/session/preload, exact frame/window/request/session/one-use-ID binding, inaccessible prompt APIs from the ordinary portfolio, malformed kinds/fields, replay/duplicate/unsolicited/stale messages and malicious content rendered as inert text. Test nonselectable phrase recording, separate masked word challenges checked in Go, wrong-word/cancel handling, DOM/buffer clearing before replies, hidden/destroyed windows and delayed delivery, no clipboard change, password reauthentication for pending legacy/resumed setup. Owner update (2026-10-27) authorizes a separate Settings backup display after explicit confirmation and current app-password verification on every invocation. Test wrong password, confirmation/password/display cancellation, locked/pending/failed state, stale UI boundaries, exact numbered phrase equality, repeat authentication and unchanged root/completion/generation/journal/ciphertext. Bind `recoveryBackup` only to `backupPhrase`; neither ordinary requests/results nor other prompt kinds may carry the words. Test fresh installation import availability and all supported canonical identities after restoring the displayed phrase. Test the explicit backup Copy phrase button: no automatic copy, exact Go-authored word order without numbering, argument-free IPC, no words in acknowledgments/errors, trusted frame/window/request/kind and delivered-state checks, cancellation/lock/stale rejection, failed clipboard writes and late UI completion. Setup keyboard copying and every other secret export remain blocked. Only public synthetic fixtures may be copied to an owned private test-display clipboard; never use the user desktop clipboard or retain its text/pixels in artifacts. Test files/logs/public frames still exclude phrase canaries; report intentional clipboard transport separately and clear it by terminating the owned display. Automation uses disposable/public fixtures and retains no phrase screenshots or plaintext artifacts. Legacy GTK tests do not certify the new shipped interface.

## 5. Isolation, authorization, and leakage

**TP-040 — Synthetic-canary leakage.** Use distinctive synthetic passwords, entropy, mnemonic words, seed bytes, extended keys, and derived private keys. Scan captured logs, errors, stdout/stderr, files, temporary directories, database/WAL files, crash output, process arguments/environment, IPC transcripts, clipboard, generated QR images, browser storage, and network payloads. Include hex/base64 encodings and meaningful mnemonic/secret fragments. The current exact signer-authored prompt and its scoped reply are the transient credential/phrase transport exception, plus the explicitly requested authenticated backup copy to the system clipboard; ordinary public-data replies/snapshots must contain no secrets. Test exception direction, kind, request/session/ID binding and absence from all unrelated messages. Never waive seed/private-key leakage or broadly exempt entire IPC streams. Repeat for successful, failed, cancelled, locked, restored, and crashing workflows. Canary absence demonstrates tested paths, not immunity to privileged malware or a compromised trusted Electron process.

**TP-041 — Process boundaries.** Attempt outbound DNS, TCP, UDP, HTTP, and local-network requests from the network-disabled Go signer; all must fail under the production isolation mechanism. Verify inherited framed IPC, no localhost listener, frame-size bounds, peer/session binding, timeout, malformed length handling, truncated frames, replay rejection, and orderly EOF. The Electron renderer must lack Node, filesystem, process-spawn, arbitrary IPC, and direct signing authority. Test untrusted frames/origins, navigation, popups, custom protocols, remote assets, and malicious RPC/token metadata.

**TP-042 — Approval binding.** The dedicated Electron confirmation must display Go-validated network, asset, full destination, amount, maximum fee, and every spend effect using only signer-authored details. Modify any field after preview, including change outputs, nonce, memo, token contract, calldata, or network. The prior approval must become unusable. Test stale/expired approvals, repeated clicks, cancelled prompts, concurrent windows, wrong-kind/ID replies, ordinary portfolio attempts to retrieve/respond to prompts, and spoofed confirmation messages. Reauthenticate passwords and bind authorization in Go. Document that the dedicated prompt renderer/main are trusted display/input components; compromise there can steal inputs or mislead users. Generic arbitrary-hash signing must not be exposed.

**TP-043 — Lock lifecycle.** Exercise sign/lock races before derivation, during confirmation, during signing, and before returning a result. Define and test the lock linearization point: no new signing operation succeeds afterward. Cancel pending authorizations, terminate isolated secret-bearing sessions as specified, and verify no automatic unlock after restart. Test inactivity, screen lock, suspend/resume, renderer crash, signer crash, and parent exit. Distinguish already-broadcast transactions from cancelled unsent operations; locking cannot retract an on-chain payment.

## 6. Chain acceptance matrix

Every row requires deterministic vectors, adverse cases, and actual network or node acceptance evidence. Test both receiving into a fresh account and sending back from it.

| Ethereum USDT extension | Tether's pinned Ethereum contract/legacy return rules and independent local token execution | Six decimals, full contract/chain identity, transfer calldata/event, ETH gas, empty return scoped only to USDT, revert/malformed/foreign receipt rejection | Real disposable local-node receipt/state; private funded Ethereum/Bybit roundtrip remains separate NOT_RUN |

**TP-050 — Matrix completeness.** Attach fixture IDs, exact dependency versions, network identities, and execution results to every row. Runtime checks must use an independent client or node query rather than echo the wallet's own success flag. Tests unavailable on a particular public testnet remain `NOT_RUN`; use local equivalents for development but do not call public integration complete.

**TP-051 — Chain-specific hazards.** For DCR, include leading-zero cases that actually diverge between `Child` and strict BIP32, both output trees, fake input values/scripts, duplicate outpoints, foreign change, immature outputs, regular-tree disapproval, and recovery across address gaps. Verify signatures with the official script engine. For TON, assert exact versioned StateInit and mainnet/testnet wallet IDs; never accept seqno advancement alone as proof the recipient was paid. For Aptos, distinguish original address from current authentication key. For NEAR, validate finality and execution status independently.

**TP-052 — Asset identity and precision.** Never identify assets by ticker alone. Test token/adapter address collisions, mismatched decimals, token-address-as-recipient mistakes, and sufficient ZEN with insufficient ETH gas. Core/EVM precision differences must not silently round amounts. Bridging is outside v1; a separately authorized future extension would need dedicated conversion/dust tests and explicit confirmation, because ordinary send/receive tests do not certify bridging.

## 7. Transaction state and QR behavior

**TP-060 — No duplicate payment.** Crash at each boundary: reservation, approval, signing, journal persistence, broadcast, response, and confirmation. Inject timeout-after-acceptance, connection reset, duplicate response, stale provider, and provider disagreement. Reconcile the original signed bytes/hash/action before any replacement. An unknown result must remain unknown/pending. Test account nonces, access-key nonces, Aptos sequences, TON seqnos, Core action nonces, and DCR UTXO reservations under concurrent sends. Balance and fee arithmetic must reject underflow, overflow, negative values, exponent ambiguity, and excess precision.

**TP-061 — Receive and QR.** Decode every generated QR with an independent decoder and compare it with the intended address/URI. Cover high DPI, resize, light/dark modes, long NEAR addresses, TON flags, and malformed scan input. Plain addresses that cannot encode network identity require an explicit network selection. A scan must never auto-send. Reject injected commands, unexpected URI parameters, unsupported schemes, conflicting amounts, and cross-network payment requests. Rendering an already authenticated public receive descriptor requires no private-key access, although unlocking may be required to retrieve encrypted metadata; verify locked-mode behavior against the product's privacy policy.

## 8. Packaged desktop, stress, and release

**TP-070 — Real package tests.** Install the actual complete portable desktop runtime in clean Ubuntu 24.04 and 26.04 environments, each under X11 and Wayland. Test non-root launch, sandbox operation, dedicated Electron input/confirmation focus, QR receive, send, lock/suspend, Electron phrase recording with Go word verification and fresh-install phrase restoration, upgrade, and uninstall preservation policy. Verify shipped Go commands do not depend on/open GTK windows. Never use `--no-sandbox` to pass. A container/Xvfb run alone is insufficient evidence for Wayland or OS lock behavior. Use a separately instrumented build for automation when necessary; verify the production package's fuses, debugger restrictions, sandbox flags, packaged resource integrity, and absence of test hooks separately.

**TP-071 — Bounded stress.** Use fixed seeds and a recorded reference environment. Exercise 100,000 malformed/bounded IPC requests, 10,000 mixed address/amount/URI cases, 1,000 concurrent-send scheduling scenarios against deterministic fake nodes, and repeated unlock/lock, recovery-confirmation and fresh phrase-restoration cycles with production KDF settings. Exercise prompt/reply concurrency, cancellation and stale-generation races separately from legacy GTK tests. Bound concurrency and resources; mocks must not broadcast live funds. Acceptance: no crash, race report, lost journal state, unauthorized signature, duplicate payment, or continuing memory/goroutine growth. Establish latency/RSS budgets before execution, record actual results, and explain regressions. Proposed targets are not measurements.

**TP-072 — Nightly soak.** Run a 24-hour deterministic scenario mix with RPC outages, rate limits, wallet locking, restarts, account discovery, and growing history. Record seeds, workload counts, RSS/goroutines, latency distributions, and final state reconciliation. Scheduled testnet activity uses capped dedicated test funds and separate reporting. No automated mainnet transactions.

**TP-080 — Release decision.** Mandatory CI is hermetic: unit, vector, mutation-critical, corpus/fuzz, race, local-node integration, and IPC/security checks must pass without public network dependencies. Public testnet integration is a separate explicit gate. Release requires all coverage floors, all fatal security/funds scenarios, packaged-OS matrix, recovery drill, and required network rows passed for the exact release candidate or an evidenced unchanged binary. Publish limitations honestly. Missing network execution, failed adversarial tests, unreviewed cryptographic/profile changes, or unsupported requested adapters block a claim of a complete production wallet. High coverage is evidence of exercised code, not a substitute for independent security review.

## 9. Owner-authorized Bybit Exchange acceptance

**TP-090 — Credential and transport containment.** Connect only through separate masked Electron prompts after app-password reauthentication. Verify encrypted persistence, restart/lock behavior, correct/wrong password, cancellation and absence of credentials, beneficiary fields and complete approval payloads from public snapshots, logs, arguments/environment, browser storage, clipboard and QR. Test exact official HTTPS endpoint allowlists, no redirects/environment proxy, bounded time/headers/body/nesting, duplicate/null/type confusion, redacted errors and independent HMAC vectors. Explicitly document that Bybit's signed message omits method/path/endpoint and that trusted Go core transports each API key/signature.

**TP-091 — Asset/network and deposit integrity.** Keep nine mainnet networks and twelve asset identities, adding only pinned Ethereum USDT with six decimals and ETH gas. Reject wrong networks, token-contract suffix identity, wrapped/native confusion, ambiguous routes, suspension, missing/foreign memos and excess precision. A valid deposit-address suffix may corroborate the matched full metadata contract. Drive Deposit through the actual existing wallet prepare/approve/sign/journal/reconcile pipeline and include a TON memo in the signed payment. Sending on-chain is not proof of exchange deposit credit. A matching ticker/EVM address cannot authorize a route or bridge.

**TP-092 — Exact spot execution and fees.** Exercise asset → USDT Sell and USDT → asset Buy with fixed `spot`/`Market`, correct base/quote spending units, no leverage/borrowing, minimum/maximum quantities, current precision, 0.01–1% application slippage, indicative last/bid/ask observations and separate approvals for necessary Funding/Unified transfers. Verify partial/cancelled orders, exact normalized cumulative quantities, all execution pages, no duplicate/foreign fills/cursor loops and bounded incomplete pages. Include documented tax fees and currencies; missing/null/unknown fee metadata, unexpected input-asset fees or fees exceeding gross receipts must remain UNKNOWN. No floats, silent rounding of user amounts or invented fill prices.

**TP-093 — Durable exchange state and no duplicate withdrawal.** Persist immutable identity/credential binding before first transmission; test failed persistence, one-use authorization, expiry, lock/concurrent-session races, changed key/endpoint and restart. Timeout-after-acceptance, duplicate codes and absent results must not trigger replacement. Reconcile the original order link, transfer UUID or acknowledged withdrawal ID. A lost withdrawal acknowledgment cannot be found by request-ID lookup or amount/address/time heuristics. Only individually reviewed documented preacceptance rejections may become terminal without a service receipt. Withdraw exclusively to the selected owned wallet on the exact mainnet network with master-key permission, whitelisting and forced on-chain delivery. Display fee-inclusive debit and service-reported amount/fee without guessing whether record amounts are gross or net. Exchange completion is not independently established chain credit/finality.

**TP-094 — Regional beneficiary privacy and recovery.** Validate the eight documented UAE fields, including real ISO country and valid past date, through the masked signer path; persist only encrypted data and send it only to `api.bybit.ae`. Reject omitted/malformed/unknown/duplicate/null fields, PII on other endpoints and public-renderer injection. Unimplemented Türkiye/Kazakhstan/EU/Indonesia questionnaire requirements must block withdrawals before internal funding moves. Fresh phrase restoration must recover wallet identities without pretending to restore API credentials, personal data, remote account access or the local exchange journal.

**TP-095 — Evidence and external acceptance.** Run critical-package coverage, client/signer semantic mutation controls, both authorization/tax-parser fuzz targets, race checks, UI/IPC tests and actual local USDT transaction execution with synthetic fixtures. Tie results to source/candidate identity and preserve PASS/FAIL/BLOCKED/NOT_RUN. Separately record actual packaged Exchange interaction and private Bybit account/permission/credit/fill/withdrawal acceptance; mocked provider or child processes cannot satisfy those gates. Funded external roundtrips and independent review remain NOT_RUN until explicitly authorized and executed with disposable account credentials and capped funds. No development/CI command imports real user secrets or automatically spends mainnet funds. See [Exchange checklist](docs/EXCHANGE.md) for measured local results and remaining gates.
